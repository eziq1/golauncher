# 插件渲染模型：拉取式与推送式

对应问题：R17（见 [requirements.md](requirements.md)），起因是 [Raycast 扩展调研](raycast-extensions-research.md) 里提到的"结构性差距"。

## 1. 两种模型

**拉取式（pull，golauncher 现在的做法）**：宿主决定什么时候要内容。每次输入、进入视图、执行完动作后，宿主调用插件的 `View(ctx, req)` / `RootItems(ctx, q)`，插件返回一份完整的视图快照，可以理解为一个"以查询为参数的纯函数"。导航栈、选中项、动作面板这些交互状态都由宿主的 `Controller` 持有。

**推送式（push，Raycast / React 的做法）**：插件持有状态，状态一变就重新渲染，把新的界面树推给宿主，宿主只负责显示最新的那一份。输入框的文字也只是插件状态的一部分，插件自己决定什么时候发请求、什么时候更新。

## 2. 对比

| 维度 | 拉取式 | 推送式 |
|------|--------|--------|
| 插件编写难度 | 低：写一个"给定查询返回列表"的函数就行 | 高：要管理状态和生命周期，通常需要 React 这一类运行时 |
| 异步与流式结果 | 弱：一次调用只能返回一个结果；想"先出一部分、再补全"做不到 | 强：可以先显示加载中，结果陆续到达就陆续渲染，比如流式搜索、AI 输出 |
| 实时变化（计时器、文件变化、下载进度、新的剪贴板记录） | 弱：插件没法主动更新，只能等宿主下一次来拉 | 强：数据一变就推送 |
| 复杂交互（表单校验、联动字段、多步向导） | 别扭：中间状态得来回传 | 自然：状态都在插件里 |
| 由谁控制节奏 | 宿主：可以取消过期请求、加超时、去抖 | 插件：可能推送得过于频繁，宿主需要限流 |
| 并发与一致性 | 简单：按代数丢弃过期结果即可（现有 `Controller` 就这么做） | 复杂：推送可能晚于导航到达，需要视图实例 ID 和版本号来丢弃过期推送 |
| 跨进程协议（M5 外部插件） | 简单：一问一答的 JSON-RPC | 复杂：要有订阅、回调 ID、视图挂载和卸载的生命周期、增量 diff |
| 可测试性 | 强：同样的输入得到同样的输出，`glctl` 的 golden 测试和会话重放就靠这一点 | 弱：结果和时间有关，测试得等插件"空闲"了才能断言 |
| 崩溃恢复 | 简单：插件重启后再拉一次即可 | 难：插件里的状态随进程一起丢失 |
| 资源占用 | 低：调用结束就不再占资源 | 高：每个打开的视图实例都在插件里常驻 |
| 生态兼容 | 和 Raycast 扩展不兼容 | 能对接 Raycast 扩展（[调研方案 B](raycast-extensions-research.md)） |

一句话：**拉取式简单、可控、好测，但做不了"自己会变"的界面；推送式表达力强，代价是协议、并发和测试都更复杂。**

## 3. 拉取式的不足，在现有功能里已经能看到

- 剪贴板历史视图开着的时候复制了新内容，列表不会自动刷新，要再输入一个字才会出现。
- 应用索引在后台刷新完成后，正在显示的结果不会更新。
- Everything 第一次启动时，只能显示"未运行"，等它准备好了也不会自动刷新。
- 无法做"搜索中，已找到 N 个"这种渐进式结果，也无法做可更新的进度提示。

## 4. 建议：以拉取为主，加两级推送

不改现有的编程模型，在它上面分两步增加推送能力：

**第一级：通知后再拉取（invalidate）**，成本很低，建议尽快做。

- SDK 增加 `Host.Invalidate(viewID string)`。插件发现数据变了（比如有新的剪贴板记录、索引刷新完成），就调用它。宿主收到后，如果这个视图正在显示，就按现有流程重新拉取一次。
- 插件依然只写"给定查询返回列表"的函数，宿主依然掌控节奏：会合并短时间内的多次通知、限流、取消过期请求。确定性也不受影响：`glctl` 等通知处理完再断言。
- 第 3 节列出的问题都能解决。

**第二级：推送视图快照**，随 M5 外部插件协议一起做，同时为 Raycast 兼容（方案 B）打基础。

- 协议增加 `ui/render(viewInstanceID, version, view)`：插件可以在任何时候推送一份完整的视图快照，宿主按 `viewInstanceID` 和 `version` 丢弃过期的推送。
- 导航栈、选中项、动作面板仍然由宿主持有，插件只推送内容，宿主保持对交互的控制。
- 推送的频率由宿主限制，最多和刷新率一致；视图卸载时通知插件释放状态。
- 测试和 `glctl` 的约定：等插件"空闲"之后再取快照。插件在空闲时要报告空闲。
- Raycast 兼容层（Node sidecar）在内部照常运行 React，对外通过 `ui/render` 推送，不影响 Go 插件的写法。

**不建议**整体改成纯推送：现有的确定性测试、崩溃恢复和简单的插件写法都会受影响，换来的表达力只有少数插件用得到。
