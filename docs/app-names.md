# 应用名称：用中文名找英文名的应用

对应需求：R40（见 [requirements.md](requirements.md)）。

## 1. 现象

在根搜索里输入“微信”找不到微信，必须输入“WeChat”才行。界面语言无论是英文还是简体中文都一样。按设计，拼音匹配（`wx`、`weixin` → 微信）是支持的，golden 测试 `query_pinyin` 里也有一个标题为“微信”的假应用，能正常匹配。

## 2. 调查

应用插件（`plugins/apps`）的应用列表来自 `internal/winapi/shell.InstalledApps`：枚举外壳的“应用程序”文件夹（`shell:AppsFolder`，即开始菜单的“所有应用”），每一项取 `SIGDN_NORMALDISPLAY` 显示名作为标题，再按目标或名称对应到开始菜单里的 `.lnk`。条目的关键词只有目标 exe 的文件名。

逐条核对了几种猜测（在真机上只读验证，用 `glctl query <词> --real` 和一次性的小程序；下面只记结论，不记本机的应用清单）：

| 猜测 | 结论 |
| --- | --- |
| (a) 快捷方式文件名是英文，中文名只在 `desktop.ini` 的 `[LocalizedFileNames]` 里 | **不是根因**。插件取的是 AppsFolder 的显示名，本来就是本地化后的名称。本机开始菜单里所有带 `LocalizedFileNames` 的条目，AppsFolder 给出的都是本地化名（其中约四分之一与文件名不同） |
| (b) AppsFolder 显示名与文件名不一致 | 同上，插件用的就是显示名，即开始菜单显示的名字 |
| (c) 商店应用 `ms-resource:` 名称没有按用户语言解析 | **不是根因**。AppsFolder 的显示名已经由外壳解析过 |
| (d) exe 版本信息里的 FileDescription/ProductName 是中文 | 对这个 WeChat **不成立**：它的版本信息只有一种语言（简体中文代码页 `080404b0`），但内容是英文 “WeChat”。不过本机另有一个应用的版本信息里有中文名而开始菜单显示英文名，说明这是一个有用的通用来源 |
| (e) 匹配器不拿中文查询去匹配关键词 | **不是根因**。`core.entryMatch` 对关键词同样做拼音展开（权重 0.95） |
| (f) 卸载注册表的 DisplayName 是“微信” | 不成立：这台机器上的 WeChat 由包管理器安装，没有卸载项；`MuiCache` 里的 FriendlyAppName 也是 “WeChat” |

开始菜单本身显示的也是 “WeChat”（系统显示语言为英文，`shell.Application` 读出的 AppsFolder 名称和 `.lnk` 显示名都是 “WeChat”）。

## 3. 根因

**系统里根本没有“微信”这个名字。** 这台机器上的 WeChat 由包管理器安装，快捷方式叫 `WeChat.lnk`，exe 的版本信息、MuiCache 也都只有 “WeChat”。应用插件已经用了外壳的本地化显示名（开始菜单显示什么，标题就是什么），所以无论怎么换取名的 API，都得不到中文名。官方安装程序在中文系统上会创建“微信”快捷方式，那种情况本来就能搜到（golden 里的假应用就是这种）。

换句话说：一个应用在系统里只登记了一个名字时，用户按它在另一种语言里的常用名搜索就找不到。中文用户用英文系统时，这对国内应用尤其常见。

## 4. 方案

保持标题不变（仍是开始菜单显示的名字），把应用的“别名”加进关键词。关键词同样参与拼音匹配，所以加入“微信”后，“微信”“weixin”“wx” 都能匹配。别名有三个来源：

1. **快捷方式文件名**（`shell`）：开始菜单显示本地化名称而 `.lnk` 文件名不同时（例如德文系统上的系统工具），把文件名也加为关键词，两种名字都能搜。
2. **exe 版本信息里的非拉丁文字名称**（`shell`）：读取目标 exe 所有语言的 FileDescription 和 ProductName，只取含非拉丁字母（中文、日文、俄文等）且不超过 40 个字符的名称。只取非拉丁文字，是因为英文名通常就是标题本身，或是 “Electron” 之类的通用名，加进来只会带来误匹配；`®` 这类符号不算字母。以下情况不读：目标在 Windows 目录下，或者有多个应用指向同一个 exe（`cmd.exe`、运行时等宿主程序的版本信息描述的不是应用本身）、目标不是 `.exe`、商店应用。
3. **常见应用的名称对照表**（`plugins/apps/names.json`）：按 exe 文件名（不区分大小写）列出一组常见国内应用的中英文名，例如 `wechat.exe`、`weixin.exe` → “微信”“WeChat”“Weixin”。这是给系统里只有一种名字的情况兜底的，数据随程序发布，以后可以继续补充；不是对某个应用写死的特殊分支。

`shell.App` 新增 `Keywords` 字段（随索引缓存保存）；插件组装条目时，关键词依次为 exe 文件名、`Keywords`、对照表中的名称，去掉与标题相同的和重复的（不区分大小写）。

**性能**：版本信息只在枚举时读一次，结果进入索引缓存，搜索时没有额外开销；对照表在第一次用到时解析一次。在一台约 300 个应用的机器上测得：完整枚举约 2.4 秒（主要花在外壳枚举和读快捷方式上），其中读取全部 exe 版本信息约 70–100 毫秒（文件已在缓存中）。枚举本来就在后台进行，不影响打开窗口和搜索。

**已知局限**：

- 关键词匹配的权重是标题的 0.95。输入 `wx` 时，如果另一个应用的英文标题恰好也能按首字母匹配（例如 “W… (X…)” 这样的名字），它可能排在 WeChat 前面；WeChat 仍在结果里，用过一次后靠使用频率就会排到前面。输入“微信”或 `weixin` 时排在第一。
- 对照表只覆盖列出的应用。其他只登记了英文名、版本信息里也没有中文名的应用，仍然要用英文名搜索。用户自定义应用别名可以作为后续需求。

## 5. 测试

- `internal/winapi/shell`：`TestAddKeywords` 用虚构的应用和假的版本信息解析函数，覆盖本地化快捷方式名、中文/日文版本名、英文和带 `®` 的版本名被忽略、共享宿主和 Windows 目录下的 exe 不读版本信息、过长的说明被忽略、与标题相同的名称被去掉；`TestNonLatin` 覆盖文字判断。
- `plugins/apps`：`TestKeywords` 覆盖“WeChat.exe 只有英文名”这一报告的场景（得到“微信”），以及与 shell 关键词的合并和去重；`TestKnownNames` 检查对照表格式。
- `internal/core`：`TestEntryMatchChineseKeyword` 确认英文标题的条目能按中文关键词及其拼音、首字母匹配。
- golden：`query_pinyin` 的“微信”条目多了关键词 “WeChat”（来自对照表），其余 golden 不变。
- 真机测试 `TestRealAppKeywords`（`internal/winapi/shell`）：设置 `GOLAUNCHER_APPS_TESTS=1` 才运行，只读，只输出数量和耗时，不输出应用名称。
- 手工验证（真机，只读）：`glctl query 微信 --real`、`glctl query weixin --real` 都把 WeChat 排在第一。
